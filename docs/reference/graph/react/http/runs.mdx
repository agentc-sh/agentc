---
title: Runs
description: The native HTTP endpoints for starting, cancelling, reattaching to, and reading runs.
---

A run is one execution of the graph within a session. These endpoints list and read runs, start runs
either attached to the original streaming request or detached in the background, cancel visible runs,
and open live Server-Sent Events streams to active runs.

`POST /v1/runs` starts an attached run and streams events on the same response. If that response is
dropped before the run finishes, the run is cancelled. `POST /v1/runs/start` starts a detached run and
returns its IDs immediately; the run continues after the response is sent. Use
`GET /v1/runs/{run_id}/events` to observe live events from a running run, and
`PUT /v1/runs/{run_id}/cancel` to explicitly cancel a visible run.

## Cancel a run

Cancel a visible run by ID.

<Endpoint method="PUT" path="/v1/runs/{run_id}/cancel">
  Cancel a run by ID.
</Endpoint>

Cancellation is idempotent for a run that exists in the caller's tenant. The endpoint returns
`204 No Content` whether the call transitions a running run to cancelled or the run was already in a
terminal state. A run that does not exist and a run that belongs to another tenant both return `404`.

## Reattach to run events

Open a live Server-Sent Events stream to a run that is currently running.

<Endpoint method="GET" path="/v1/runs/{run_id}/events">
  Stream live events for a running run from this point forward.
</Endpoint>

Reattachment is live-only. The stream receives events produced after the request attaches; it does not
replay events that were produced earlier. Dropping this stream closes only this observer and does not
cancel the run. Use `PUT /v1/runs/{run_id}/cancel` when the client wants to stop the run.

<Parameters in="path">
  <Field name="run_id" type="string">
    The run ID.
  </Field>
</Parameters>

<Responses>
  <Response status="200" description="A stream of events (text/event-stream).">
    The event payloads use the same `RunEvent` variants documented for `POST /v1/runs`.
  </Response>
  <Response status="404" description="Run not found." />

returns `404`.

## Reattach across replicas

Reattach uses pub/sub to deliver live run events to `GET /v1/runs/{run_id}/events` streams. By
default, generated standalone agents use an in-memory transport with no external service:

```bash
export AGENT__PUBSUB__KIND=memory
export AGENT__PUBSUB__CAPACITY=4096
```

The in-memory transport is process-local. If a deployment has multiple replicas and a reattach request
may land on a different process than the one executing the run, configure the Redis-compatible
transport:

```bash
export AGENT__PUBSUB__KIND=redis
export AGENT__PUBSUB__URL=redis://localhost:6379
```

Dragonfly can provide that Redis-compatible pub/sub service:

```yaml title="compose.yaml"
services:
  dragonfly:
    image: docker.dragonflydb.io/dragonflydb/dragonfly
    ulimits:
      memlock: -1
    ports:
      - 6379:6379
```

Pub/sub carries live events only. It does not store run history or replay missed events. Cancelling a
run is persisted through the shared database and does not depend on pub/sub.

### ModelConfig

Per-run model call configuration. Timeout and retry values supplied here take precedence over
manifest and startup defaults independently. Omitted values continue to use the corresponding
startup defaults. The `override` object controls model selection and inference parameters only for
this run.

<Fields label="ModelConfig">
  <Field name="override" type={<>{<Link href="#modelconfigoverride">ModelConfigOverride</Link>} | null</>}>
    Optional provider, model, and inference parameter overrides.
  </Field>
  <Field name="timeout" type="integer | null">
    Maximum time in milliseconds to establish the model response stream. This does not limit the
    duration of an established stream.
  </Field>
  <Field name="retry" type={<>{<Link href="#modelconfigretry">ModelConfigRetry</Link>} | null</>}>
    Retry policy for transient failures while establishing the model response stream.
  </Field>
</Fields>

AG-UI clients can supply the same object through `forwarded_props.model`. It is interpreted by the
ReAct adapter and does not add fields to the AG-UI protocol itself.

### ModelConfigOverride

Per-run overrides for the agent's configured model. Any omitted field falls back to the manifest
configuration.

<Fields label="ModelConfigOverride">
  <Field name="provider" type="string | null">
    Provider name to use instead of the configured one.
  </Field>
  <Field name="model" type="string | null">
    Model identifier to use instead of the configured one.
  </Field>
  <Field name="inference_params" type={<>{<Link href="#inferenceparams">InferenceParams</Link>} | null</>}>
    Inference parameter overrides.
  </Field>
</Fields>

### ModelConfigRetry

Retry policy for transient failures before the model response stream is established. A response
stream that has already started is not retried.

<Fields label="ModelConfigRetry">
  <Field name="max_attempts" type="integer">
    Maximum number of attempts, including the first request.
  </Field>
  <Field name="initial_backoff" type="integer">
    Delay in milliseconds before the first retry.
  </Field>
  <Field name="max_backoff" type="integer">
    Maximum base backoff between attempts, in milliseconds. Jitter may add a small delay after the
    base backoff is capped.
  </Field>
</Fields>
